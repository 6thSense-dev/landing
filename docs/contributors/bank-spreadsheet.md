# Contributor bank spreadsheet

`/upload#payment-details` accepts an account holder name (including Korean), bank name and Korean account number after the current payment notice is accepted. Select from 25 Korean banks and financial institutions, or choose **Other — enter bank name** (**기타 은행 직접 입력**) to type an unlisted name; the selection and custom name survive retries and language changes. It does not call Wise. Existing payout links and financial history remain unchanged. Older mobile bank-write endpoints return HTTP410 directing people to the website.

Notice `KR-PAYMENT-SHEET-2026-09-19-2` requests two separate choices: `collects_details` and `international_transfer`. The page shows a short summary and expandable provider/overseas-processing details. New receipts record only these requested choices; do not add affirmative storage/staff-access or account-ownership acknowledgments that the contributor was not asked to make, or rewrite historical consent receipts. The API still requires the current notice version/hash and locale.

Keep the complete disclosure in each locale's `paragraphs` for older open browser pages; newer pages use `summary` plus `details`. Both `/privacy` and `/privacy/synapse` publish `frontend/src/seo/payment-notice.json`, a snapshot of `public_notice()` from `backend/app/core/payment_notice.py`. Regenerate that snapshot whenever the notice changes and check its complete JSON content, including version/hash, against the backend before release. For this transition, deploy the Apps Script validator accepting the two choices first, then the compatible frontend and public snapshot, then the API serving notice `-2`. The API's version/hash check requires fresh acknowledgment when a contributor still has an older notice.

The authenticated backend identifies the contributor; the browser cannot supply a contributor ID. It sends an HMAC-SHA256 envelope to `scripts/google-contracts/BankDetails.gs` in the existing contractor Apps Script project. Deploy that script as an owner-executed web app with anonymous HTTP access: every request still requires the server HMAC. Append the file without replacing the current contract source or its triggers.

Run `setupBankDetails` once to create the [**Bank details** tab](https://docs.google.com/spreadsheets/d/1ZJZ_H4ZIWRl_c6QngmsDTfcAhQnbN6vrLbUnpPd_CPg/edit#gid=1958393299) in the existing private workbook. Public/domain link sharing is rejected. Existing explicit workbook collaborators can read the new tab; keep workbook access limited to authorized personnel. Store a random secret of at least 32 characters as the Apps Script property `BANK_DETAILS_SECRET`, and set matching Railway API variables `CONTRIBUTOR_PAYMENT_SHEET_SECRET` and `CONTRIBUTOR_PAYMENT_SHEET_URL` (the deployed `/exec` URL). Never put the secret in source, the browser bundle, logs or a sheet cell.

The bridge checks the HMAC and a five-minute timestamp window, validates headers and privacy, and serializes writes with a script lock. One row per contributor prevents duplicate saves, even when a browser retries with a new operation ID. Account numbers are text so leading zeros survive. Formula-like names are escaped. Success is returned only after a write, flush and read-back; the returned receipt contains only name, bank, last four digits, timestamp and submission ID. The app database saves that masked receipt as `sheet_saved` with a null Wise recipient ID. A status lookup recovers saves whose HTTP response or DB receipt was lost. Failed requests retain entries in browser memory; use **Check saved status** or retry without reloading the page. Fields are cleared after a confirmed receipt or an explicit cancel; unsaved entries do not survive closing or reloading the page.

Bank requests lock only their contributor’s Wearer row, with a two-second database lock timeout. They do not share the global footage-scanner locks. Account deletion updates that row too. During deletion fulfillment, the bridge sets a permanent contributor-ID tombstone under the same script lock and removes bank rows, then reads back to confirm removal. The tombstone prevents a delayed request from restoring erased details. This cleanup runs even when no DB receipt exists. Spreadsheet failure leaves deletion retryable and never reports completion. Minimal retained settlement evidence must be handled under the existing staff retention process.

For corrections, staff should verify the contributor’s identity and update the spreadsheet row deliberately. Registration does not automatically overwrite an existing account. Do not delete or change contributor IDs or submission IDs. The website’s masked DB receipt is a record of the submitted details, not a live view of staff corrections; tell the contributor when a correction is completed.

Validation: Python tests cover auth, consent, minimal fields, masking, retries, no Wise calls, scanner-lock isolation, existing payout links and deletion cleanup. Node mocks cover bridge HMAC, leading zeros, formula safety, deduplication and deletion tombstones. Playwright covers mobile/tablet/desktop success, lost responses, safe retry and language changes. Production verification must also exercise the deployed bridge and confirm workbook write/read-back with clearly marked synthetic data, followed by cleanup.
